📘 FastAPI Project — Полное руководство пользователя

Единый документ: описание системы, все связи, каждый файл, каждый шаг запуска, мониторинг, логи, статистика, работа с клиентами и новые запросы.
Стек: FastAPI + ARQ + Redis + PostgreSQL + OpenTelemetry + Grafana.

1. Введение

Этот проект — асинхронный сервис интеграции с Битрикс24. Он принимает вебхуки от Битрикс24, надёжно сохраняет их в PostgreSQL, а фоновый воркер постепенно отправляет вызовы в REST API Битрикс24, соблюдая лимиты (rate limit).

Ключевая идея
Система не отправляет данные в Битрикс «в лоб». Сначала задача надёжно сохраняется в БД (outbox), и только потом воркер её выполняет. Если Битрикс упал — задача не потеряется, воркер повторит попытку. Если Redis упал — задача останется в БД.

Что даёт эта архитектура:

  • ✅ Задача не теряется при падении Redis.
  • ✅ Задача не теряется при падении Worker (retry 3 попытки).
  • ✅ Повторный вебхук не создаёт дубль (идемпотентность по key).
  • ✅ Видно статус каждой задачи: pending → enqueued → processing → done / failed / dead.
  • ✅ Сквозная трассировка: путь запроса от FastAPI до Worker виден в Grafana Tempo.
  • ✅ Метрики: RPS, latency p95, ошибки 5xx, размер очереди.
  • ✅ Автоматический retry: упавшие задачи перезапускаются сами (до 25 раз).

2. Общая картина

Система — это три больших блока, связанных через базу данных:

  Клиент / Битрикс24 (вебхук)
        │
        ▼
  ┌─────────────┐     ┌──────────────────┐     ┌─────────────┐     ┌──────────────┐
  │  FastAPI    │────▶│  PostgreSQL      │◀────│   Worker    │────▶│  Bitrix24    │
  │  (app/)     │     │  tasks_outbox    │     │  (worker/)  │     │  REST API    │
  └─────────────┘     └──────────────────┘     └─────────────┘     └──────────────┘
        │                    ▲                        │
        │                    │                        │
        └────────── core/ ───┴────────────────────────┘
                (общая доменная логика)

Всё, что между API и Worker, — это core/: общая логика, которую используют оба слоя. Именно поэтому в графе зависимостей core стоит в центре, а не дублируется в API и воркере.

4. Слои системы

Проект разделён на слои. Чем выше слой — тем он «умнее», чем ниже — тем он «техничнее».

🧠 core/ — Доменная логика outbox.py, rate_limiter.py, bitrix_batch.py, publisher.py, bitrix_client.py
⚙️ worker/ — Исполнение tasks.py, settings.py
🧩 adapters/ — Ваши запросы base.py, bitrix_*.py (по одному на запрос)
🗄️ migrations/ — Схема БД env.py, versions/*.py
Правило зависимостей
app → core ← worker. API и воркер знают про core, но core не знает про них. Если тебе нужно, чтобы core импортировал что-то из app или worker — это сигнал, что логика лежит не на своём месте.

5. Паттерн Outbox (и автоматический retry)

Это главное, что нужно понять. Разберём по шагам, что происходит при создании задачи:

Клиент шлёт POST-запрос в API
Например, «создать сделку в Bitrix». Эндпоинт: app/main.py.
API валидирует данные
Вызывает core/outbox.py::create_task(). Эта функция пишет строку в таблицу tasks_outbox со статусом pending.
API отвечает клиенту «202 Accepted»
Задача принята, но ещё не выполнена. Клиент не ждёт Bitrix.
Издатель (cron каждые 2 сек) перекладывает задачи в Redis
core/publisher.py::publish_pending() читает pending из БД, кладёт в Redis, меняет статус на enqueued. Если Redis лежит — не падает, задача остаётся в БД.
Worker берёт задачу из Redis
worker/tasks.py::process_outbox_task() забирает пачку (до 25 задач), переводит статус в processing, ставит processing_started_at.
Worker выбирает адаптер по типу события
Автообнаружение через pkgutil: adapters/bitrix_deal_add.py, adapters/bitrix_contact_add.py и т.д.
Отправка через HTTP-клиент с учетом лимитов
core/bitrix_client.py собирает URL, отправляет POST. Учитывается rate limit (capacity=50) и batch (до 25 задач за раз).
Успех → done. Ошибка → failed + retry_count++
Если Bitrix вернул 500 или лимит, задача получает статус failed, retry_count = 0. Специальный cron retry_failed_tasks вернёт задачу в pending и увеличит retry_count. После 25 попыток задача уходит в dead, чтобы не блокировать очередь.
Watchdog спасает зависшие задачи
Cron requeue_stale_tasks каждые 5 минут возвращает в pending задачи, которые висят в processing дольше 5 минут.
Почему так, а не напрямую?
Если API будет вызывать Bitrix напрямую: (1) клиент будет ждать по 5–30 секунд; (2) при падении Bitrix задача потеряется; (3) не получится соблюдать rate limit. Outbox решает все три проблемы сразу.

Горячие точки — что чинить в первую очередь

🔴 Приоритет 1: worker/tasks.py — 11 исходящих связей
Воркер напрямую дёргает telemetry (2×), rate limiter (3×) и БД (5×). Это «жирная» функция. Разбей на:
  • fetch_pending_tasks() — выборка из БД
  • send_to_bitrix(task) — отправка
  • mark_done() / mark_failed() — обновление статуса
Тогда каждая функция тестируется отдельно, а process_outbox_task становится тонкой обёрткой-оркестратором.
🟡 Приоритет 2: main.py
Вынеси в app/bootstrap.py: 
# bootstrap.py
async def create_app() -> FastAPI: ...
async def init_db() -> None: ...
def init_telemetry() -> None: ...

# main.py — только запуск
if __name__ == "__main__":
    uvicorn.run(...)
Степень main.py упадёт с 13 до 2–3.
🟡 Приоритет 3: db.py
Раздели на два файла:
  • app/db/engine.py — только engine и sessionmaker
  • app/db/base.py — только Base
Модели будут импортировать только base, не таща за собой engine.
🟡 Приоритет 4: два файла outbox.py
app/models/outbox.py и core/outbox.py — путаница. Переименуй:
  • app/models/outbox.py — оставить (это модель)
  • core/outbox.py → core/outbox_service.py (это логика)

# scripts/report.py
import asyncio
from app.db import SessionLocal
from sqlalchemy import text

async def report():
    async with SessionLocal() as session:
        result = await session.execute(text("""
            SELECT status, COUNT(*),
                   AVG(EXTRACT(EPOCH FROM (updated_at - created_at))) as avg_seconds
            FROM tasks_outbox
            WHERE created_at > NOW() - INTERVAL '1 hour'
            GROUP BY status
        """))
        print("=== Отчёт за последний час ===")
        for row in result:
            print(f"{row[0]}: {row[1]} задач, среднее время: {row[2]:.2f} сек")

asyncio.run(report())

22. Добавление нового запроса к Bitrix24 (адаптер)

Правило: один запрос = один файл-адаптер. Хотите 10 запросов — 10 файлов. Каждый файл маленький и не пересекается с другими.

22.1. Что внутри адаптера

# adapters/bitrix_deal_add.py — ВАШ файл, только для этого запроса
EVENT = "ONCRMDEALADD"          # тип события от Битрикс24
METHOD = "crm.item.add"         # метод API
ENTITY_TYPE_ID = 1302           # параметр (сделка)

def build_fields(payload: dict) -> dict:
    # маппинг: что взять из payload и положить в fields
    return {
        "title": payload["data"]["FIELDS"]["TITLE"],
        "stageId": payload["data"]["FIELDS"]["STAGE_ID"],
    }

22.3. Как добавить новый адаптер (пошагово)

Запустите генератор
python scripts/new_adapter.py bitrix_deal_add crm.item.add 1302 ONCRMDEALADD
Генератор создаёт новый файл
Из шаблона adapters/_template.py → adapters/bitrix_deal_add.py. Другие файлы не трогает.
Вы заполняете созданный файл
Открываете adapters/bitrix_deal_add.py, дописываете build_fields() под свой запрос.
Всё. Больше ничего не трогаете
worker/tasks.py сам найдёт адаптер через pkgutil — не нужно вручную регистрировать.
Итог: при добавлении нового запроса вы работаете только с одним файлом (adapters/bitrix_deal_add.py). Генератор создаёт его, автообнаружение подхватывает.

28. Чек-листы поддержки

Ежедневно

  • Размер очереди pending не растёт
  • Нет задач в processing старше 5 минут
  • Доля failed за сутки < 5%
  • Воркер отвечает (health-check)

Еженедельно

  • Просмотреть топ-10 ошибок в last_error
  • Проверить, не заканчивается ли место в БД (outbox растёт)
  • Проверить актуальность токена Bitrix (срок действия)
  • Прогнать alembic current — совпадает ли с head

Перед релизом

  • Миграции протестированы на staging
  • alembic upgrade head проходит без ошибок
  • Тесты зелёные
  • Конфиг валидируется (Pydantic не падает)
  • Версия задеплоена сначала на staging, потом на prod
  • После деплоя — проверить первые 10 задач прошли успешно

При инциденте

  • Остановить воркер, если ошибки массовые
  • Зафиксировать trace_id проблемных задач
  • Найти паттерн в last_error
  • Проверить, не изменился ли API Bitrix (их changelog)
  • После фикса — массово сбросить failed → pending осознанно
  • Написать post-mortem: что сломалось, почему, как предотвратить

Операционные сценарии

✅ Клиент говорит «задача не выполнилась»
  1. Найди задачу: SELECT * FROM tasks_outbox WHERE payload::text LIKE '%<ключ>%'
  2. Посмотри status и last_error
  3. Если failed — проверь, повторяется ли ошибка (retry_count растёт?)
  4. Найди trace_id и посмотри трейс в Grafana Tempo
  5. Если ошибка Bitrix — проверь их статус-страницу и лимиты
⚠️ Воркер «завис» — задачи не уходят
  1. Проверь, жив ли процесс воркера: ps aux | grep arq
  2. Проверь очередь: SELECT status, COUNT(*) FROM tasks_outbox GROUP BY status;
  3. Если много processing — воркер упал, не успев обновить статус. Нужен watchdog: задачи в processing старше N минут → вернуть в pending
  4. Проверь логи воркера
⚠️ Клиент жалуется на дубли
  1. Проверь app/models/idempotency.py::IdempotencyKey — работает ли дедупликация
  2. Проверь, передаёт ли клиент Idempotency-Key заголовок
  3. Если нет — попроси клиента добавить, или включи дедупликацию по payload
🔴 Массовый сбой (много failed)
  1. Останови воркер, чтобы не усугублять
  2. Найди общий паттерн в last_error: SELECT last_error, COUNT(*) FROM tasks_outbox WHERE status='failed' GROUP BY last_error ORDER BY COUNT(*) DESC;
  3. Если Bitrix вернул 401 — проверь токен в app/config.py / .env
  4. Если rate limit — снизь скорость в core/rate_limiter.py
  5. После фикса — сбрось статус: UPDATE tasks_outbox SET status='pending' WHERE status='failed' AND ...
Главное правило безопасности
Не редактируй tasks_outbox вручную без бэкапа. Это единственный источник правды о том, что не доставлено в Bitrix. Перед любым UPDATE — CREATE TABLE tasks_outbox_backup AS SELECT * FROM tasks_outbox WHERE status='failed';
