🚨 Реагирование на инциденты — Runbook

Что делать, когда что-то сломалось: как найти причину, какие показатели считать критичными, и в каком порядке смотреть.
Открывайте этот файл, когда пришла тревога или клиент говорит «не работает».

1. Главный принцип: не гадать, а смотреть

У вас есть три источника информации, и у каждого своя роль. Не пытайтесь решить проблему одним из них — используйте все три вместе [citation:1].
ИнструментНа какой вопрос отвечаетКогда смотреть
Метрики (Grafana, Prometheus)«Что-то вообще не так?» (ошибки, задержка, очередь)Первым делом — увидеть, что проблема есть, и где она примерно.
Трассы (Tempo)«Где именно внутри запроса сломалось или зависло?»Вторым — когда знаете, что проблема есть, но не знаете, в каком сервисе/шаге.
Логи (uvicorn, arq, PostgreSQL)«Почему это сломалось?» (конкретная ошибка, стектрейс)Третьим — когда нашли виновника, но нужна причина.
Ошибка новичка: сразу лезть в логи и читать тысячи строк. Сначала посмотрите на графики — они покажут, куда смотреть. Логи — только для подтверждения причины.

3. Первичная диагностика (за 2 минуты)

Откройте Grafana → дашборд fastapi_project
Смотрите на 4 панели: «Очередь задач», «RPS», «p95 Latency», «Ошибки 5xx».
Определите, какой показатель «красный»
Если очередь растёт — проблема в Worker. Если ошибки 5xx — проблема в FastAPI. Если latency — проблема в БД или внешнем API.
Проверьте, все ли контейнеры живы
podman ps — Redis, PostgreSQL, Collector, Prometheus, Tempo, Grafana должны быть Up.
Проверьте, запущены ли процессы
pkill -f uvicorn не нужен, просто проверьте: ps aux | grep -E 'uvicorn|arq'. Оба должны быть.

4. Сценарии: что случилось → что делать

Сценарий A: Очередь pending растёт и не падает

Симптом: График «Очередь задач» показывает, что pending растёт (10, 20, 50...), а done не увеличивается.

Причина: Worker не забирает задачи из Redis (или не может их выполнить).

Проверьте, запущен ли Worker
В терминале с arq должны идти логи cron:publish_pending. Если тишина — Worker упал. Запустите: arq worker.settings.WorkerSettings.
Проверьте Redis
podman exec fastapi_project_redis_1 redis-cli ping → должно быть PONG. Если нет — podman-compose up -d.
Проверьте, видит ли Worker задачи
В логах Worker должно быть publisher: enqueued task .... Если есть, но process_outbox_task не начинается — проблема в Redis-очереди.
Проверьте БД (не завис ли Worker на запросе)
podman exec fastapi_project_postgres_1 psql -U fastapi -d fastapi_db -c "SELECT pid, state, query FROM pg_stat_activity WHERE state != 'idle';" — если видите долгий SELECT или UPDATE, возможно, БД тормозит.

Сценарий B: Ошибки 5xx (FastAPI возвращает 500)

Симптом: Панель «Ошибки 5xx» показывает ненулевые значения.

Причина: Исключение внутри FastAPI (необработанная ошибка).

Посмотрите в терминал с uvicorn
Там будет Traceback. Ищите последнюю строку (SomeError: ...). Это и есть причина.
Если traceback нет — найдите trace_id упавшей задачи
В Grafana → Tempo → TraceQL → { status = error } или { resource.service.name = "fastapi-project" && status = error }.
Проверьте, не связано ли с БД
Если в traceback видите asyncpg или sqlalchemy — проблема в подключении к PostgreSQL. Проверьте podman ps (контейнер postgres).

Сценарий C: Latency высокая (запросы медленные)

Симптом: «p95 Latency» > 2 секунд.

Причина: Медленная БД, медленный внешний API (Битрикс24), или сам Worker тормозит.

Найдите медленную трассу
Grafana → Tempo → TraceQL → { duration > 2s }. Откройте самую долгую.
Посмотрите, какой спан долгий
Если process_outbox_task долгий — проблема в Worker (вызов Битрикс24 или БД). Если POST /... долгий — проблема в FastAPI (БД).
Проверьте БД
podman exec fastapi_project_postgres_1 psql -U fastapi -d fastapi_db -c "SELECT query, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;" (если расширение включено). Или просто посмотрите на pg_stat_activity.

Сценарий D: RPS резко упал

Симптом: График RPS падает в 2 раза и больше.

Причина: Либо запросы перестали приходить (Битрикс24 не шлёт вебхуки), либо FastAPI не принимает (порт, сеть).

Проверьте, живы ли FastAPI
curl http://127.0.0.1:8000/health → {"status":"ok"}. Если нет — процесс упал.
Проверьте, идут ли запросы вообще
В терминале uvicorn должны появляться строки POST /webhook/bitrix ... 200 OK. Если нет — проблема на стороне Битрикс24 (не шлёт) или сеть.

5. Шпаргалка запросов (быстро найти причину)

В Grafana / Prometheus

# Очередь по статусам
tasks_outbox_count

# Ошибки 5xx (должно быть пусто)
rate(http_requests_total{status=~"5.."}[5m])

# Самые медленные эндпоинты (p95)
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

# RPS
rate(http_requests_total[1m])

В Grafana / Tempo (поиск проблемных трасс)

# Все трассы с ошибкой
{ status = error }

# Трассы дольше 2 секунд
{ duration > 2s }

# Трассы конкретного сервиса
{ resource.service.name = "fastapi-worker" }

# Трассы конкретного клиента (если есть tenant_id)
{ resource.tenant.id = "client_1" }

В терминале (SQL к БД)

# Что сейчас выполняется в БД (долгие запросы)
podman exec fastapi_project_postgres_1 psql -U fastapi -d fastapi_db \
  -c "SELECT pid, state, query FROM pg_stat_activity WHERE state != 'idle';"

# Последние упавшие задачи (с ошибкой)
podman exec fastapi_project_postgres_1 psql -U fastapi -d fastapi_db \
  -c "SELECT id, status, last_error FROM tasks_outbox WHERE status='failed' ORDER BY updated_at DESC LIMIT 5;"

# Задачи, которые зависли в pending > 5 минут
podman exec fastapi_project_postgres_1 psql -U fastapi -d fastapi_db \
  -c "SELECT id, created_at FROM tasks_outbox WHERE status='pending' AND created_at < NOW() - INTERVAL '5 minutes';"

6. Разбор полётов (после того как починили)

Когда проблема решена, не просто закройте вкладку. Запишите три вещи в файл INCIDENTS.md (создайте в корне проекта):

  1. Что случилось (симптом: «очередь выросла до 200»).
  2. Почему случилось (причина: «Worker упал из-за OOM» или «Redis перезагрузился без AOF»).
  3. Что сделали, чтобы не повторилось (например: «Добавили алерт на pending > 20», «Включили AOF в Redis»).
Зачем это: через месяц вы забудете, почему очередь росла. Записи спасут вас (и клиента) от повторения той же ошибки. Это стандартная практика SRE — «postmortem culture» [citation:8].
Готово. Теперь у вас есть не просто инструменты, а методика: что смотреть, какие пороги считать критичными, и что делать в каждом сценарии. Когда что-то сломается — откройте этот файл, найдите симптом, выполните шаги.
