1. Введение

Этот проект — асинхронный сервис интеграции с Bitrix24. Он принимает запросы от клиентов, ставит задачи в очередь в базе данных и фоновый воркер постепенно отправляет их в Bitrix, соблюдая лимиты API.

Ключевая идея
Система не отправляет данные в Bitrix «в лоб». Сначала задача надёжно сохраняется в БД (outbox), и только потом воркер её выполняет. Если Bitrix упал — задача не потеряется, воркер повторит попытку.

Всё, что между API и Worker, — это core/: общая логика, которую используют оба слоя. Именно поэтому в графе зависимостей core стоит в центре, а не дублируется в API и воркере.

3. Слои системы

Проект разделён на слои. Чем выше слой — тем он «умнее», чем ниже — тем он «техничнее».

🌐 app/ — API-слой main.py, config.py, db.py, telemetry.py
🧠 core/ — Доменная логика outbox.py, rate_limiter.py, bitrix_batch.py, publisher.py
⚙️ worker/ — Исполнение tasks.py, settings.py
🗄️ migrations/ — Схема БД env.py, версии миграций
Правило зависимостей
app → core ← worker. API и воркер знают про core, но core не знает про них. Если тебе нужно, чтобы core импортировал что-то из app или worker — это сигнал, что логика лежит не на своём месте.

4. Паттерн Outbox — сердце системы

Это главное, что нужно понять. Разберём по шагам, что происходит при создании задачи:

1
Клиент шлёт POST-запрос в API с данными (например, «создать сделку в Bitrix»).
2
API валидирует данные и вызывает core/outbox.py::create_task(). Эта функция пишет строку в таблицу tasks_outbox со статусом pending.
3
API отвечает клиенту «202 Accepted» — задача принята, но ещё не выполнена. Клиент не ждёт Bitrix.
4
Воркер периодически опрашивает БД, забирает пачку задач со статусом pending и переводит их в processing.
5
Воркер вызывает process_outbox_task(), который через BitrixRateLimiter соблюдает лимиты API и отправляет данные в Bitrix.
6
Успех → статус done. Ошибка → failed + запись last_error, задача вернётся в очередь на повтор (retry).
Почему так, а не напрямую?
Если API будет вызывать Bitrix напрямую: (1) клиент будет ждать по 5–30 секунд; (2) при падении Bitrix задача потеряется; (3) не получится соблюдать rate limit. Outbox решает все три проблемы сразу.

7. God-ноды — что это и почему не всегда плохо

«God-нода» — узел с максимальным числом связей. Не всегда это болезнь. Бывает здоровый хаб (стабильный, низкая частота изменений) и жирный объект (меняется часто, тянет всё).

db.py10 (7 вход.) Риск Разделить на db/engine.py + db/base.py
core/outbox.py9 (0 вход.) Проверить Если никто не импортирует — мёртвый код или динамика
worker/tasks.py9 Горячая точка Разбить на подфункции, вынести rate-limit

8. Горячие точки — что чинить в первую очередь

🔴 Приоритет 1: core/outbox.py с 0 входящих связей
Все 9 связей модуля — исходящие. Никто его не импортирует. Либо это мёртвый код, либо он загружается через importlib (что хуже для поддержки). 
# Проверь:
grep -rn "from core.outbox" .
grep -rn "import core.outbox" .
grep -rn "core\.outbox" .
Если пусто — удаляй. Если динамика — замени на явный импорт и покрой тестами.
🔴 Приоритет 2: worker/tasks.py — 8 исходящих связей
Воркер напрямую дёргает telemetry (2×) и rate limiter (3×). Это «жирная» функция. Разбей на:
  • fetch_pending_tasks() — выборка из БД
  • send_to_bitrix(task) — отправка
  • mark_done() / mark_failed() — обновление статуса
Тогда каждая функция тестируется отдельно, а process_outbox_task становится тонкой обёрткой-оркестратором.
🟡 Приоритет 3: main.py
Вынеси в app/bootstrap.py: 
# bootstrap.py
async def create_app() -> FastAPI: ...
async def init_db() -> None: ...
def init_telemetry() -> None: ...

# main.py — только запуск
if __name__ == "__main__":
    uvicorn.run(...)
Степень main.py упадёт с 12 до 2–3.
🟡 Приоритет 4: db.py
Раздели на два файла:
  • app/db/engine.py — только engine и sessionmaker
  • app/db/base.py — только Base
Модели будут импортировать только base, не таща за собой engine.
🟡 Приоритет 5: два файла outbox.py
app/models/outbox.py и core/outbox.py — путаница. Переименуй:
  • app/models/outbox.py → оставить (это модель)
  • core/outbox.py → core/outbox_service.py (это логика)

9. Что и как редактировать

Практические сценарии с указанием файлов:

➕ Добавить новое поле в задачу
  1. Создай миграцию: alembic revision -m "add field X"
  2. Отредактируй файл в migrations/versions/ — добавь op.add_column(...)
  3. Обнови модель app/models/outbox.py::TaskOutbox — добавь mapped_column
  4. Если поле нужно при создании — обнови core/outbox.py::create_task()
  5. Если поле нужно при обработке — обнови worker/tasks.py
  6. Прогони alembic upgrade head
➕ Добавить новый endpoint
  1. Создай роутер в app/ (например, app/routes/xxx.py)
  2. Подключи в app/main.py через app.include_router(...)
  3. Валидацию данных — в Pydantic-схеме (отдельный файл app/schemas/)
  4. Постановку задачи — через core/outbox.py::create_task()
➕ Добавить интеграцию с новым API (не Bitrix)
  1. Создай core/new_api_client.py
  2. Создай core/new_api_rate_limiter.py по образцу BitrixRateLimiter
  3. Добавь тип задачи в tasks_outbox (поле task_type, если ещё нет)
  4. В worker/tasks.py добавь ветвление по task_type или отдельный воркер
🔧 Изменить rate limit Bitrix
  1. Найди core/rate_limiter.py
  2. Константы лимитов должны быть в app/config.py, не хардкодом
  3. Если хардкод — вынеси в настройки, чтобы менять без деплоя
🔧 Добавить retry-политику
  1. В TaskOutbox должны быть поля retry_count и next_retry_at
  2. В worker/tasks.py::mark_failed() — инкремент retry_count, расчёт next_retry_at (exponential backoff)
  3. В выборке воркера — фильтр WHERE next_retry_at <= NOW()
  4. При retry_count > MAX — статус dead (не повторять, нужен ручной разбор)

10. Работа с клиентами — операционные сценарии

✅ Клиент говорит «задача не выполнилась»
  1. Найди задачу: SELECT * FROM tasks_outbox WHERE payload::text LIKE '%<ключ>%'
  2. Посмотри status и last_error
  3. Если failed — проверь, повторяется ли ошибка (retry_count растёт?)
  4. Найди trace_id и посмотри трейс в Jaeger/Grafana Tempo
  5. Если ошибка Bitrix — проверь их статус-страницу и лимиты
⚠️ Воркер «завис» — задачи не уходят
  1. Проверь, жив ли процесс воркера: ps aux | grep worker
  2. Проверь очередь: SELECT status, COUNT(*) FROM tasks_outbox GROUP BY status;
  3. Если много processing — воркер упал, не успев обновить статус. Нужен watchdog: задачи в processing старше N минут → вернуть в pending
  4. Проверь логи воркера
⚠️ Клиент жалуется на дубли
  1. Проверь app/models/idempotency.py::IdempotencyKey — работает ли дедупликация
  2. Проверь, передаёт ли клиент Idempotency-Key заголовок
  3. Если нет — попроси клиента добавить, или включи дедупликацию по payload
  4. Проверь, нет ли двойной отправки: задача done, но Bitrix её не получил → проблема в транзакции между БД и Bitrix (классическая проблема outbox — нужна идемпотентность на стороне Bitrix)
🔴 Массовый сбой (много failed)
  1. Останови воркер, чтобы не усугублять
  2. Найди общий паттерн в last_error: SELECT last_error, COUNT(*) FROM tasks_outbox WHERE status='failed' GROUP BY last_error ORDER BY COUNT(*) DESC;
  3. Если Bitrix вернул 401 — проверь токен в app/config.py / .env
  4. Если rate limit — снизь скорость в core/rate_limiter.py
  5. После фикса — сбрось статус: UPDATE tasks_outbox SET status='pending' WHERE status='failed' AND ...

SQL-запрос для дашборда

-- Состояние очереди прямо сейчас
SELECT
  status,
  COUNT(*) AS cnt,
  MIN(created_at) AS oldest,
  MAX(updated_at) AS newest
FROM tasks_outbox
WHERE created_at > NOW() - INTERVAL '24 hours'
GROUP BY status
ORDER BY cnt DESC;
Совет
Заведи алерт: если COUNT(*) задач в pending за 5 минут не уменьшился — значит, воркер не работает. Это самый частый сбой.

12. Чек-лист поддержки

Ежедневно

  • Размер очереди pending не растёт
  • Нет задач в processing старше 5 минут
  • Доля failed за сутки < 5%
  • Воркер отвечает (health-check)

Еженедельно

  • Просмотреть топ-10 ошибок в last_error
  • Проверить, не заканчивается ли место в БД (outbox растёт)
  • Проверить актуальность токена Bitrix (срок действия)
  • Прогнать alembic current — совпадает ли с head

Перед релизом

  • Миграции протестированы на staging
  • alembic upgrade head проходит без ошибок
  • Тесты зелёные
  • Конфиг валидируется (Pydantic не падает)
  • Версия задеплоена сначала на staging, потом на prod
  • После деплоя — проверить первые 10 задач прошли успешно

При инциденте

  • Остановить воркер, если ошибки массовые
  • Зафиксировать trace_id проблемных задач
  • Найти паттерн в last_error
  • Проверить, не изменился ли API Bitrix (их changelog)
  • После фикса — массово сбросить failed → pending осознанно
  • Написать post-mortem: что сломалось, почему, как предотвратить
Главное правило
Не редактируй tasks_outbox вручную без бэкапа. Это единственный источник правды о том, что не доставлено в Bitrix. Перед любым UPDATE — CREATE TABLE tasks_outbox_backup AS SELECT * FROM tasks_outbox WHERE status='failed';
