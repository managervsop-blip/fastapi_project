📘 FastAPI Project — Руководство

Интеграции с Битрикс24 через REST API. Стек: FastAPI + ARQ + Redis + PostgreSQL.
Открывайте этот файл при каждом запуске, редактировании и отладке.

1. Что это

Это рабочая среда для интеграций с Битрикс24. Она принимает вебхуки от Битрикс24, надёжно сохраняет их в базу данных, а потом выполняет вызовы к API Битрикс24 в фоне — так, чтобы ни одно событие не потерялось, даже если что-то упало.

Всё живёт в одной папке ~/Sergey_doc/fastapi_project/. Её можно бэкапить, переносить на другой ПК или сервер — и всё восстановится.

2. Главная идея: Outbox-паттерн

Проблема: если FastAPI сразу кладёт задачу в Redis, а Redis в этот момент недоступен — задача теряется навсегда.
Решение: FastAPI сначала пишет задачу в PostgreSQL (таблица tasks_outbox, статус pending). Потом отдельный «издатель» (cron каждые 2 секунды) перекладывает её в Redis. Если Redis упал — задача остаётся в БД. Когда Redis оживает — издатель подхватывает её.

Что это даёт:

  • ✅ Задача не теряется при падении Redis.
  • ✅ Задача не теряется при падении Worker (retry 3 попытки).
  • ✅ Повторный вебхук не создаёт дубль (идемпотентность по key).
  • ✅ Видно статус каждой задачи: pending → enqueued → done / failed.

.env · .env.example
🗄️ Данные → PostgreSQL
Задачи (tasks_outbox), ключи (idempotency_keys), бизнес-данные.
app/models/*.py · migrations/
⚙️ Код → файлы .py
Логика: эндпоинты, задачи воркера, адаптеры, ядро.

app/config.py
Пример: новая интеграция со SmartCargo. Токен — в .env (SMARTCARGO_API_KEY=...), поле — в app/config.py (smartcargo_api_key: str = ""), код — в adapters/smartcargo.py, данные — в PostgreSQL через модель в app/models/.

4. Поток данных (от Битрикс24 до Битрикс24)

Сверху вниз — что происходит с событием. Под каждым шагом — файлы, которые за него отвечают.

1
🔔 Битрикс24 (внешний)
Шлёт вебхук (HTTP POST) с событием. Секрет вебхука — в .env. Методы API: crm.item.add, user.get и т.д.
.env (B24_WEBHOOK_URL) БАЗОВЫЙ
2
⚡ FastAPI (приём)
Принимает payload, проверяет application_token, вызывает create_task(payload, key=event_id), отвечает 200 OK сразу.
app/main.py ПОЛУБАЗОВЫЙ · app/config.py БАЗОВЫЙ
3
🗄️ PostgreSQL (надёжное хранилище)
Таблицы tasks_outbox (задачи) и idempotency_keys (защита от дублей). Задача в статусе pending.
app/models/outbox.py · app/models/idempotency.py · migrations/ БАЗОВЫЙ
4
📤 Издатель (cron каждые 2 сек)
Читает pending из БД, кладёт в Redis, обновляет статус на enqueued. Если Redis лежит — не падает.
core/publisher.py БАЗОВЫЙ · worker/settings.py (cron) ПОЛУБАЗОВЫЙ
5
📬 Redis (очередь ARQ, AOF)
Быстрая очередь. AOF (appendonly yes) — переживает перезапуск.
docker-compose.yml · .env (REDIS_URL) БАЗОВЫЙ
6
⚙️ Worker (обработчик)
Берёт задачу из Redis, выбирает адаптер по типу события (автообнаружение), вызывает adapter.execute(payload). Retry: 3 попытки.
worker/tasks.py ПОЛУБАЗОВЫЙ · worker/settings.py ПОЛУБАЗОВЫЙ
7
🧩 Адаптеры (ВАШИ файлы)
Один запрос = один файл. В каждом: EVENT, METHOD, ENTITY_TYPE_ID, build_fields().
adapters/base.py БАЗОВЫЙ · adapters/bitrix_deal_add.py ВАШ · adapters/bitrix_contact_add.py ВАШ
8
🌐 HTTP-клиент (базовый)
Собирает URL (B24_WEBHOOK_URL + METHOD), отправляет POST с fields, обрабатывает коды ошибок (QUERY_LIMIT_EXCEEDED, OPERATION_TIME_LIMIT), retry.
core/bitrix_client.py БАЗОВЫЙ · .env (B24_WEBHOOK_URL) БАЗОВЫЙ
9
🔔 Битрикс24 REST API (внешний)
Выполняет метод (crm.item.add), возвращает result.item, time.operating.
10
↩️ Возврат в Worker
После успеха — mark_done() (статус done). При ошибке — mark_failed() (статус failed + last_error).
worker/tasks.py · core/outbox.py БАЗОВЫЙ

6. Адаптеры (ваши запросы к Битрикс24)

Правило: один запрос = один файл-адаптер. Хотите 10 запросов — 10 файлов. Каждый файл маленький и не пересекается с другими.

Что внутри адаптера

# adapters/bitrix_deal_add.py — ВАШ файл, только для этого запроса
EVENT = "ONCRMDEALADD"          # тип события от Битрикс24
METHOD = "crm.item.add"         # метод API
ENTITY_TYPE_ID = 1302           # параметр (сделка)

def build_fields(payload: dict) -> dict:
    # маппинг: что взять из payload и положить в fields
    return {
        "title": payload["data"]["FIELDS"]["TITLE"],
        "stageId": payload["data"]["FIELDS"]["STAGE_ID"],
    }

Кто выбирает адаптер

# worker/tasks.py — автообнаружение (не трогаете при новых адаптерах)
import pkgutil, importlib
from adapters import __path__ as adapters_path

ADAPTERS = {}
for _, name, _ in pkgutil.iter_modules(adapters_path):
    if name.startswith("bitrix_"):
        mod = importlib.import_module(f"adapters.{name}")
        ADAPTERS[mod.EVENT] = mod

# в process_outbox_task:
adapter = ADAPTERS[payload["event"]]
result = await adapter.execute(payload)

7. Генератор файлов из шаблона

Идея: чтобы не писать каждый адаптер с нуля, есть генератор. Он создаёт новый файл из шаблона. Не трогает другие файлы. Вы заполняете только созданный файл.

Как работает

Запускаете генератор
python scripts/new_adapter.py bitrix_deal_add crm.item.add 1302 ONCRMDEALADD
Генератор создаёт новый файл
Из шаблона adapters/_template.py → adapters/bitrix_deal_add.py. Другие файлы не трогает.
Вы заполняете созданный файл
Открываете adapters/bitrix_deal_add.py, дописываете build_fields() под свой запрос.
Всё. Больше ничего не трогаете
worker/tasks.py сам найдёт адаптер через pkgutil — не нужно вручную регистрировать.
Итог: при добавлении нового запроса вы работаете только с одним файлом (adapters/bitrix_deal_add.py). Генератор создаёт его, автообнаружение подхватывает. Базовые файлы (core/, .env, config.py) — не трогаете.

8. Как запускать

Правило №1: в каждом новом терминале сначала активируйте venv.
Активировать venv (в каждом терминале)
cd ~/Sergey_doc/fastapi_project && source venv/bin/activate
Поднять Redis и PostgreSQL
podman-compose up -d → проверить: podman ps
Запустить FastAPI (терминал №1)
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
Запустить ARQ Worker (терминал №2)
arq worker.settings.WorkerSettings
Проверить (терминал №3)
curl http://127.0.0.1:8000/health → {"status":"ok"}

9. Как останавливать

ЧтоКак
uvicornCtrl+C в терминале №1, дождаться $.
arq workerCtrl+C в терминале №2.
Redis + PostgreSQLpodman-compose down (данные в томах).
Всё сразуpkill -f uvicorn, pkill -f arq, podman-compose down.
Частая ошибка: закрыть терминал с uvicorn без Ctrl+C → порт 8000 занят → Address already in use. Лечится: pkill -f uvicorn.

ЧтоКак

Перенос на новый ПК/сервер

  1. Скопировать папку без venv/.
  2. sudo apt install python3 python3-venv redis-server postgresql git podman podman-compose
  3. python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt
  4. Создать .env из .env.example.
  5. podman-compose up -d → alembic upgrade head.
  6. Восстановить БД (если нужно): podman exec -i fastapi_project_postgres_1 psql -U fastapi fastapi_db < backup_db.sql
  7. Запустить uvicorn и arq.

14. Правила (шпаргалка)

  1. Каждый новый терминал — сначала source venv/bin/activate.
  2. Переменные — в .env. Данные — в PostgreSQL. Код — в .py. Настройки — в app/config.py.
  3. Один запрос = один адаптер (adapters/bitrix_*.py). Не смешивайте.
  4. Новый адаптер — через генератор scripts/new_adapter.py. Базовые файлы не трогаете.
  5. Изменили worker/tasks.py или worker/settings.py — перезапустите воркер (Ctrl+C → arq ...).
  6. Изменили модель — alembic revision --autogenerate → alembic upgrade head.
  7. Не коммитьте .env и venv/ в git.
  8. Функция для ARQ — первым аргументом ctx.
  9. Слои не нарушать: app/ не знает про worker/, adapters/ не знает про БД.
  10. Бэкап — папка без venv/ + дамп БД + .env отдельно.
